# Framework Selection and Architecture Requirements

- Select from confirmed feasibility; adding no framework is valid. Explain recommendations, gaps, applicability, and conditions for revisiting exclusions. Document all components from input to outcome with inputs, outputs, interfaces, responsibilities, acceptance, and failure handling. Obtain explicit architecture approval before implementation.
- Classify direct reuse, thin adaptation, business rules, and custom algorithms. Specify necessity, upstream versus owned contracts/configuration/tests, upgrade impacts, and replacement/retirement conditions. Internal functions may reference component responsibilities. Open source still needs maintenance; disclose forks, copied code, patches, and reimplementations rather than calling them thin adaptation.
- Custom code requires confirmed business rules, interface glue, or demonstrated gaps. First review failure evidence/interface limits, minimal implementation, maintenance cost, and configuration/composition/scope alternatives. Dependency, licensing, or maintenance objections require evidence.
- Reuse workflows/contracts through parameters, configuration, or necessary adapters. Explain shared/additional maintenance; test a real second input when available, otherwise mark reuse unverified. Avoid per-example programs, duplicated storage/query/validation, and speculative frameworks.
