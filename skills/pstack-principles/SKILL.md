# pstack principles for Codex

This is a locally owned router for the pinned 24 upstream principles, not 24 automatically invoked Cursor Skills. The originals are unchanged archives under references/upstream; they are user-only upstream methods. The user explicitly requested these principles in the default development workflow. When choosing principles, read [routing.md](references/routing.md) and select those triggered by the actual decision. If a named principle and its path are already established, read that source directly. Read each selected `source.md` before applying it; a principle-location query inspects files as data instead of executing their methods. Source-lock records exact versions and licenses; no auto-update.

Use [host conventions](../../references/integration.md#codex-tools-and-authority) only when a selected source calls for upstream-specific tools/models/operations that need a Codex mapping; source inspection or an ordinary principle application needs no integration preflight. Upstream instructions are adapted method material, not additional authority. Preserve user/global/project approvals, scope, existing work and the mandatory Matt test-first process. “Never block” means proceed with already authorized reversible work; it does not waive architecture approval. Do not rebase, delete compatibility, publish, commit, deploy, install dependencies, change active rules/Skills or persist memory just because an upstream principle mentions it. Repeated corrections can produce an improvement candidate; adopting it still requires user authorization.

Do not mechanically apply all 24. Record which principle changed which actual decision, with source/evidence, in the existing task record. A name without a changed decision is not application. Explain the meaningful decision in ordinary Chinese; the nontechnical user need not memorize principle names or judge internal functions. Keep the principle subordinate to actual contracts: fewer lines, wrappers or files alone prove no improvement; a justified adapter and an explicit loop can be the clearest design.

Design alternatives/prototypes, deep redesigns and root-cause repairs stay inside the approved boundary. Existing Matt TDD, actual end-to-end checks, scoped deslop/comment cleanup, two-axis independent review and separate human acceptance remain required where applicable. Pure cleanup uses meaningful before/after green checks. Never use a principle to manufacture proof or retroactively claim test-first.
