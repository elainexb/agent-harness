## Code-review input and runtime adaptation

Read this section only for an actual invocation of the installed `code-review` method. It adapts input/tool conditions, not Matt's two-axis algorithm or a software lifecycle. Resolve that Skill from its observed native path.

- **Actual input:** apply the fixed-input section below. Preserve the user's chosen base/range or selected file scope, meaningful staged/unstaged changes and necessary untracked contents. Give both leaves the same candidate, baseline, Spec and relevant rule identities. Commit-only commands are not WIP evidence. An absent meaningful baseline limits what can be reviewed; never manufacture proof with a commit or silent scope reduction.
- **Execution:** use available fresh contexts (`fork_turns="none"` where supported), no model override and at most two leaves in a round. Dispatch the two actual axes together when both are available and wait for their results. Bind the allowed files, actual input artifacts and reading/tool limits in each brief. Forbid writes, external effects, recursive delegation, the other reviewer's output, unrelated private history and app/model/test runs outside separate authority. The coordinator performs authorized running checks. Missing fresh contexts leave independence incomplete; self-review is not a substitute. Brief restrictions are not OS-enforced isolation.
- **Evidence:** retain actual prompts, public outputs, tool calls/results and observed runtime/model identity in existing permitted records. A reviewer self-description is not actual tool evidence. Exclude secrets and hidden reasoning. Findings remain separate Standards/Spec judgments tied to the real input, not a merged vote or whole-product certificate.
- **Additional Standards:** for a review supporting behavioral handoff or preserving a legacy independent-code-review request, give only the Standards leaf the applicable [local strict-quality lens](review/strict-quality.md) and required sources. Explicitly requested stricter Standards use the same input mechanism. This preserves the local quality threshold without loading Delivery Assurance or starting a third reviewer. Ordinary review otherwise uses Matt's existing project-rule/smell baseline.
- **Bounded recheck:** default ceiling is one initial round and at most one affected re-review, at most two leaves per round, within any tighter approved budget. Review-only authorizes no repair or automatic retry. Count already executed rounds; changing method/entry or entering delivery assurance never resets the budget. Covered repairs belong to the current implementation task; after candidate changes, only still-supported evidence remains reusable. Unresolved blockers/uncertainty at the ceiling are reported incomplete.

## Fixed input and project records

Before authorized edits or a review/comparison requiring change identity, retain an identified baseline, including relevant pre-existing work. An ordinary read-only location answer needs no change snapshot. At review time fix the actual candidate and all selected changes: committed, staged, unstaged and necessary untracked files. Use exact commits plus saved diffs and file identities for Git work. Never call only `git diff base...HEAD` sufficient for uncommitted work. Never commit or stage user work just to make review possible.

For non-Git projects use a clear selected-file list, prior/current content and identities; if no meaningful baseline exists, say what can and cannot be reviewed. Use fresh scoped copies when necessary; avoid copying credentials, production data or whole unrelated directories. Relevant caller/context files can be read without counting their pre-existing issues as introduced regressions.

Reuse the project's authoritative task/design/check records. Add a small task record only when needed. Keep one source for each requirement, glossary, business assertion and acceptance state. In a local demo, missing tracker configuration can be represented by that local task record; do not create external issues or labels without authorization. A missing requirement is not a passing Spec review.

For complex work with dependent milestones, or cross-session work, use those existing records to connect the requested outcome and applicable milestones to actual execution state, exit evidence and its input/version, unresolved dependencies, and the next permitted action with its approval/resource conditions. Existing map/spec/ticket fields and links are sufficient; detailed decisions/evidence remain at their established owners. Expand the current step as needed and keep later steps coarse. A simple answer needs no extra record, template or planning method; read-only work keeps necessary continuation state in the permitted response/session.

At a milestone boundary, compare its observed result with its exit criteria and the requested outcome. Identify the remaining prerequisite or outcome that actually needs work, then check the existing authority and remaining resources. If covered, continue and select the method for that concrete next operation through native discovery and its invocation policy; a Skill boundary creates no new approval gate. Otherwise report the specific blocked condition or pending decision and continue only independent authorized work. Completion of the requested design/review may correctly end the task while implementation remains unapproved.

Track execution progress separately from evidence support and approval/acceptance. A closed ticket or finished phase is not proof of whole-task completion, user acceptance or adoption. When relevant inputs change, retain historical observations but reassess affected evidence and dependent readiness before using them to advance. This section defines record relationships, not a new task manager or a mandatory lifecycle.
