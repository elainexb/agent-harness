# Startup assessment and pinned source profile

This Reference owns new-effort alignment and the local installation/profile facts for Matt Pocock's pinned methods. It is neither a callable Skill nor an executable lifecycle router. Global owns authorization, stage and delivery gates; installed methods own their procedures. Ordinary resumed work needs no startup reload.

## Startup assessment

Use this alignment guidance when a new software effort needs it; it is not a prerequisite for native Skill selection or ordinary resumed work.

1. Inspect relevant project instructions, existing task/map/spec/tickets, real examples and confirmed decisions. Establish final scope, minimum end-to-end outcome, exclusions, assumptions and observable acceptance. Investigate facts; select needed interviewing through native discovery and follow that method's own entry and invocation policy.
2. Assess applicable pinned Matt methods using their native names/descriptions and the actual invocation policy. Reuse an existing valid assessment. Select the method needed now, with only its necessary prerequisites; neither a new effort nor method uncertainty mandates reading an unselected router's body. When the user actually requests `ask-matt`, preserve its installed explicit-only policy. Otherwise resolve an actionable remaining method/approval gap without automatically entering that router.
3. For a complex or cross-session effort, use the existing approved task/map/spec/tickets with the [continuation record convention](integration.md#fixed-input-and-project-records). Reuse its goal, dependencies and evidence rather than create another plan. A routine phase sequence needs no coordinator Skill; use an installed orchestration method only when its scope and invocation authority apply.

The pinned profile supplies provenance when a version/source question matters, not a manual discovery Registry. Native descriptions remain the selection surface; reading Skill files as the explicit subject of an inspection is a different activity.

## Dependency and upstream maintenance

Read this section only for a Skill dependency/source question or an authorized update-impact proposal. Ordinary method execution needs only its actual branch dependencies.

- **Direct dependencies belong to the consumer.** Its existing SKILL.md invocation/loading instruction owns the target and condition: required for the invoked method, conditional on a stated branch, or a supporting resource. State the input/output or assumption relied upon where it is not evident. Keep longer details in that consumer's existing Reference, with a conditional pointer. Descriptions remain discovery contracts; source citations, navigation lists and archived examples are not executable dependency declarations. A named dependency preserves its actual invocation policy and grants no new effects.
- **Source facts belong to the existing lock/profile.** Identify the upstream by repository, path and pinned revision, with retained hashes and licenses. The Matt profile is a historical installation receipt; its active_files/body_unchanged describe that recorded installation, not every later derivative. Preserve those facts. Local changes are identified by the reviewed Candidate diff and file identities, or the adopted revision when one exists. A source archive is provenance or selected method material, not another installed dependency.
- **Adaptation belongs to its maintained owner.** The consuming Skill owns its local entry/method adaptations; each shared Reference owns its stated host/evidence/quality contract. Keep any source-lock adaptation_owner pointer current. Bind an update proposal's changed local assumptions to affected existing cases/verification evidence; link those records instead of copying their verdicts into a lock. Do not rewrite upstream originals to describe local changes.
- **Impact is derived on demand.** Compare the pinned and proposed upstream versions before proposing adoption. Inspect affected source paths, entry/policy changes, inputs/outputs, method/resource requirements and local adaptation assumptions. Follow declared direct consumers, then their affected consumers, retaining branch conditions and recording each visited relation once. References participate as resource dependencies; attribution/navigation alone does not propagate execution impact. Produce potentially affected, confirmed incompatible, unaffected-for-this-change or UNKNOWN findings with evidence. Record unresolved dynamic/external consumers rather than claim an exhaustive graph.
- **Verification stays scoped and separately authorized.** Propose existing static checks for identities/paths/policy and the smallest behavioral cases for changed contracts. Reuse still-valid evidence; hashes and unchanged declarations do not establish semantic compatibility. Update-impact analysis does not run checks, upgrade packages, change invocation permissions or adopt a candidate. Keep the resulting impact note in the existing change/review record; there is no separately maintained reverse registry.

## Shared reference ownership and lifecycle

The tree at `~/.codex/harness/references/` is a user-level Harness documentation asset, separately owned from every installed Skill package. Each existing document retains its specific authority: integration owns host adaptation; implementation owns software case/local evidence additions; debugging owns local diagnostic safeguards; verification, cleanup, human-review and feedback-regression own their stated disciplines. The review/ subtree owns local Standards lenses and pinned provenance, with no callable manifest or review coordinator. This section owns only asset maintenance and retirement. Global owns authorization and gates; installed Skills own their methods. This is not a Router, Registry or executable lifecycle.

- **Install/update:** install Skills in their actual native Skill roots, not this shared tree. A Skill update/reinstall may update that Skill's package within its approved scope; it must not overwrite or garbage-collect these externally owned documents or their pinned source assets as “unused Skill files.” Shared changes require a separately reviewed Harness candidate under existing approval rules.
- **Migrate/retire the old entry:** migrate the existing References and all their dependencies as one identified tree, preserving internal relative layout, original source bytes, licenses and provenance. Update known live consumers to the new root. Before removing an old asset path, establish the intended destination contents and caller-path coverage; if those are incomplete, stop the affected retirement. Deleting only the retired `coding-workflow/SKILL.md` does not authorize deleting its References before migration. Do not leave the authoritative copy inside a directory scheduled for package deletion.
- **Skill cleanup/uninstall:** after migration, removing the old `.agents/skills/coding-workflow/` package cannot remove the authoritative shared tree because it is physically outside both `.agents/skills/` and `.codex/skills/`. Do not traverse external shared assets as package-owned dependencies. A cleanup tool offering only deletion of a broader parent/root is not suitable for that operation; preserve the shared data and stop that deletion.
- **Shared asset retirement:** a Reference, archive, license or profile is removable only as an explicit Harness change after its live consumers are removed or migrated and retained evidence/provenance needs are resolved. A Skill disappearing from discovery, a package upgrade or absence of a local manifest is not a shared-resource retirement signal. Keep one authoritative tree, not runtime copies under each Skill.

These are ownership/maintenance rules, not a claim of filesystem protection or an implemented installer safeguard. A future migration must verify the actual destination and necessary live pointers before cleanup; this Candidate alone moves no files.
