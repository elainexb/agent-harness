# Prove the important behavior

This Reference owns real-path verification. Read its applicable branch when evidence for the accepted surface or risk-bearing effects is required; it does not start a test run without authorization. The [prove-it-works source](upstream/pstack/principle-prove-it-works/source.md) is supporting principle material, not a second default verification method. For risk-bearing changes read [pstack blast-radius](upstream/pstack/blast-radius/source.md), identify the real state/call/protocol paths beyond the diff and one or two facts on which safety depends. Exercise reachable counterexamples rather than inventing hypothetical concerns. For cancellation/retry/cleanup, explicitly inspect the precedence of cancellation, unconfirmed cleanup and diagnostic errors; validate relevant combinations rather than only each event alone.

Use the project's existing accepted behavior checks and verification Skill first; reuse current applicable receipts rather than rerun solely for a phase label. Keep the real build/version, preconditions, expected/observed state, important side effects and teardown visible.

## Verification scope and missing capability

Authorized development/verification can cover writing or updating behavior checks and fixtures at the approved seams with existing tools, and executing the agreed real surface within its effects and resource limits. Those routine steps need no new approval when already covered. A readiness inspection or case-design-only request does not authorize execution.

A missing driver, tool or reusable recipe is an evidence gap, not authority to build verification infrastructure. Creating a new Verification Skill, reusable harness/driver or testing facility requires scope approval that actually covers those artifacts and their effects; general development/verification authority alone is insufficient. Reuse such approval when it already exists. Otherwise describe the smallest proposed addition, affected files/dependencies, effects and validation cost, and stop that construction pending approval. Continue independent authorized checks; leave the unsupported path explicitly unverified and delivery incomplete rather than weakening its criteria.

Only when that scope covers a project-local recipe, use installed `create-verification-skill` at its native catalogue path to discover actual commands/tools and prepare the scoped guide. Recipe creation authority does not include actual Smoke execution. Launch, doctor, drive, evidence collection and cleanup for that Smoke run require execution authorization covering the mapped feature, effects and resource limits. One existing approval may cover both creation and execution when it actually states that scope; reuse it without another approval request. If only creation is covered, deliver the unexecuted recipe with Smoke status NOT_RUN and stop before running it. The archive [upstream guide](https://github.com/cursor/plugins/blob/8b3326d99fd4b993cb33a24dad8af03175c642c5/pstack/skills/create-verification-skill/SKILL.md) supplies provenance. New frameworks/dependencies, broader trials or changes to approved architecture retain their applicable gates; a recipe's generated steps do not authorize their own execution.

For a UI, operate the actual accepted surface when tools permit it. For a CLI, run a real command with actual fixture/input. For data/output, check values and meaning against the independent expected result, not only counts/exit codes. Never lower a check or substitute another version to get a pass.

Before a runnable feature/demo handoff, the accepted end-to-end path must actually run. If a needed UI tool, environment or permission is absent, report the exact gap and mark that delivery incomplete. CLI-only evidence cannot prove the UI works. A verification guide or generated helper is draft until its real mapped path has been exercised and evidence survives cleanup. Map verified, partially verified and unverified features explicitly; one smoke run does not certify all features.

Label actual production/model use, controlled adapter tests, fault injection and static reasoning separately. Preserve the real command/argv, cwd, relevant environment, code/test/input identity, exit status, output and unknowns. Existing historical checks do not establish the current candidate passed. A script can report a failure; only the requirement and actual observation establish what that failure means.
